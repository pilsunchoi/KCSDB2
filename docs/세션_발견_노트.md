## 1. 데이터 함정 (실측 확인)

### 1.1 나미비아 ISO2='NA' → pandas NULL 오변환

외교부 국가표준코드 CSV에서 나미비아의 ISO2 코드는 `NA`다. pandas `read_csv`의 기본 `na_values`가 이를 결측(NaN)으로 오변환한다. 처리 없이 dim_country를 만들면 나미비아가 조인 키 결측으로 탈락하고, 관세청이 나미비아를 NA로 집계할 경우 매칭 실패한다.

- 해결: `pd.read_csv(..., keep_default_na=False, na_values=[""])`
- 검증: 이 처리로 iso2 결측 0, 나미비아 'NA' 문자열 정상 보존 확인.
- 계열: 메모리에 기록된 "'NULL' 문자열 리터럴 함정"과 동일 계열(문자열이 결측 토큰으로 오인되는 문제).

### 1.2 관세청 API는 결측과 0을 구분하지 않는다

원본 XML 3종(202401_US, 200701_US, 202401_AD) 전체에서 수치 태그(expDlr/impDlr/expWgt/impWgt/balPayments)는 항상 존재하며, 값이 없으면 0으로 채워져 온다. 결측 태그 0건.

- 귀결: "관측값 없으면 NULL" 원칙은 이 데이터에 적용 불가능. 원본에 NULL이 없다.
- 귀결: `int(값 or 0)`의 `or 0`은 도달하지 않는 방어코드. 결측 손실 아님.
- 202606 프로브 결과가 방증: 미공개월은 items=0(빈 응답)으로 오지, 잠정치를 임의값으로 채우지 않는다.

### 1.3 dim_hs10 한글품목명은 최말단 세분만 담는다

관세청 HS부호 파일의 `한글품목명`은 HS10 최말단 서술만 담는다. 예: `0101211000` = "농가 사육용", `0101291000` = "경주말". 이것이 말(馬)인지 상위 맥락이 없다. 상위 분류는 `성질통합분류코드명`("(말)")에 일부 있으나 불완전.

- 성격: 관세청 파일 자체의 구조적 한계. 파싱·설계 오류 아님.
- 처리: dim_hs10은 이 값을 raw 그대로 담는다. 완전한 품목 서술이 필요하면 상위 HS 코드 조인 또는 HS6 concordance로 분석 계층에서 해결. DB가 서술을 합성하지 않는다.

### 1.4 HS 개정 연계표는 PDF이나 추출 안전

관세청 FTA 포털 HS 연계표 3종은 엑셀이 아니라 150페이지 안팎 PDF. 그러나 2열(HS2022 6자리, 과거 6자리) 순수 코드쌍 구조라 pdfplumber 페이지당 1표로 정확 추출. 병합셀·다단헤더 없음. 형식 이상행 0건(1건 예외는 1.5).

### 1.5 "삭제" 폐지 표기

HS2022→2017 연계표 마지막 페이지에 `(삭제, 300219)` 행 존재. 2017년 코드 300219가 2022에서 폐지되어 대응 코드 없음을 뜻함. 관세청이 폐지 코드를 "삭제" 문자열로 일부 표기.

- 처리: `relation='deleted'`로 보존(제거 아님). 품목 퇴출 정보는 개정 간 품목 연속성을 다루는 분석에서 쓰일 수 있으므로 삭제하지 않는다.
- 다른 두 파일(2007, 2012)에는 삭제 행 없음.

### 1.6 음수 중량 (관세청 사후 정정 원본)

fact_trade에 음수 19행 존재. 전부 중량(exp_wgt/imp_wgt) 음수이고 금액(exp_dlr/imp_dlr)은 0 이상. 관세청의 중량 사후 정정(반품·수정신고로 이전 신고분 중량이 음의 조정치로 상계)이다. 2016년 US에 13행 집중, 나머지 PH·IT·PT·NZ·FR 산발.

- 파싱 오류 아님. 원본 XML에 음수 존재. 02a가 그대로 보존.
- 처리: 원칙(원본 보존)상 보존. 04 검증에서 금액음수(FAIL)와 중량음수(INFO)를 분리. 중량음수는 정상.
- 분석 영향: 단가=금액/중량 계산 시 음수 중량은 이상치. 분석 계층에서 처리.

### 1.7 관세청 월통계 2단계 공개 (잠정월 함정)

관세청은 월 무역통계를 2단계로 공개한다. 먼저 국가별 총계(잠정), 이후 HS10 품목별 확정 명세. 202604·202605는 총계만 나오고 품목 명세가 없는 중간 상태였다.

- 프로브(00_probe)가 "총계 금액>0"으로 판정해 이 두 달을 확정으로 오판했다. 판정 기준을 "품목 명세(item_count>1) 존재"로 수정.
- 02b가 fact_trade에 거래행이 0인 월(잠정월)의 fact_total을 제거. 202604·202605 각 243행, 총 486행 제외.
- 확정 범위: 200701~202603, 231개월.

### 1.8 meta_calls.item_count 결함 (총계행 미집계)

meta_calls.item_count는 수집단계(01_fetch_raw)에서 총계행을 세지 않는다. 거래 0건이나 관세청이 총계행(0값)을 반환한 페어에서 item_count=0이나 fact_total엔 1행 존재. 이런 페어 4,642개 확인.

- 귀결: item_count는 fact 행수의 대조 기준으로 부적합. 총합 비교 시 +/- 페어가 상쇄돼 잔차만 남아 오탐(차이 4) 발생.
- 04 검증 재설계: 총합 비교 폐기. "item_count>0인 페어가 fact에 적재됐는가"(수집→적재 누락 감지)로 방향 전환. 전체 실행에서 미적재 0 확인(PASS).

### 과제 1 — 폐지코드 hs10 품목명 확보

측정 결과와 두 조건부 판단.

측정: 폐지코드(dim_hs10 미매칭 hs10) 4,194종. 거래액 비중 전체 11.6%, 시기별 2007기 21.4%→2022기 0.17%. 집중도: 상위 152종이 거래액 80%, 309종이 90%. 상위 309종 중 308종(99.7%)의 hs6가 concordance 매칭.

자료 제약: data.go.kr은 과거 시점 HS부호 스냅샷을 별도 제공하지 않음(최신본 덮어쓰기). 최신 파일은 폐지코드 미수록. hs10 폐지코드의 정확한 품목명을 담은 공개 기계가독 파일은 현재 미확인. CLIP 과거 관세율표가 남은 경로이나 기계가독성 불확실.

조건부 판단:
- HS6 이하 해상도 분석: hs10 세분 품목명은 hs6 절단으로 소거되므로 불필요. hs6 계열 식별은 concordance로 대체(상위 309종의 99.7%). 이 경우 과제 1 불필요.
- HS10 세분 품목명을 쓰는 분석: 품목명 필요. 자료 확보 경로가 막혀 있어 미해결. 필요시 CLIP 조사로 재개.

현 dim에는 근사 품목명을 추가하지 않았다(raw 원칙: 관세청이 그 hs10에 부여한 명칭이 아닌 계열 근사값은 원본 아님).

### 과제 2 — concordance 미매칭 (개정 연결 손실)

측정: fact hs6의 concordance 미매칭. 시기별 올바른 버전 조인 기준.
- 거래액 기준: HS2007기 0.007%, 2012기 0.006%, 2017기 0.004%. 완전 사각지대(어느 버전 past에도 없는 hs6) 130종, 거래액 0.004%(8.3억/20.5조 천달러).
- 종수 기준: 미매칭 hs6 2007기 124종, 2012기 63종, 2017기 34종. 버전 매핑 근사오차 91종 별도.

어느 쪽이 중요한지는 분석 설계가 정한다. 관세청 직접 연계표(2007↔2012 등) 추가 확보는 개수 기반 분석에서 종수 미매칭을 줄이려면 유효하나, 자료 존재·기계가독성 미확인.

### 04_validate concordance 커버리지 측정 정정 (중요)

### 과제 3 — 쿼리 성능 실측: 완료. 인덱스 불필요 확정.

측정(2026-07-03, 로컬 DB 681MB, 27.5M행, 각 쿼리 2회 2번째 채택):
- Q1 HS6×국가×월 집계: 5.13s, 결과 1,984만 행
- Q2 YoY self-join: 5.56s, 결과 1,798만 행. **EXPLAIN ANALYZE 실제 실행시간 0.912s.**
- Q3 concordance 조인: 0.40s, 3행
- Q4 dim 3중 조인+필터: 0.095s, 3,715행

판정: **네 쿼리 모두 인덱스 불필요.**
- 순수 연산은 전부 초 단위 이내(self-join조차 0.9s). Q3·Q4는 0.1~0.4s.
- Q1·Q2의 5초는 연산이 아니라 결과 2천만 행을 pandas DataFrame으로 변환(.df())하는 비용. 인덱스로 해결 안 됨(인덱스는 연산 가속이지 결과 전송 가속 아님).
- DuckDB 컬럼저장·벡터화·정렬적재(02b의 yyyymm·stat_cd·hs10)가 인덱스 없이 충분.

**분석 계층 성능 팁 (DB 결함 아님):**
대용량 결과(수백만 행)를 통째로 파이썬(.df())으로 끌어오지 말 것. 집계를 DuckDB 안에서 완료하고 최종 소형 결과만 가져온다. 예: self-join 후 2천만 행을 넘기지 말고, DuckDB 안에서 추가 집계(국가별·기간별)해 수천 행으로 줄인 뒤 .df(). 이는 쿼리 설계 문제이지 인덱스·DB 구조 문제 아님.
