# 관세청 품목별 국가별 수출입실적 데이터베이스 만들기

이 문서는 관세청 무역통계 데이터베이스(KCSDB2)를 처음부터 다시 만들고 GitHub에 공개하기까지의 전 과정을 정리한다. 데이터베이스를 왜 만들었는지, 어떤 원칙으로 설계했는지, 데이터를 어떻게 쌓았는지, 그 과정에서 어떤 함정을 만났는지, 완성 후 무엇을 더 검증했는지, 마지막으로 어떻게 배포했는지를 다룬다.

데이터베이스나 프로그래밍에 익숙하지 않은 사람도 이해할 수 있도록 용어를 풀어서 설명한다. 실행에 필요한 구체적 절차는 저장소의 개별 문서(DB_구축_원칙.md, 세션_발견_노트.md, 배포자_안내.md)에 있고, 이 문서는 그것들을 하나로 엮는 이야기다.

문서에 나오는 수치는 실제 데이터 전체(2007년 1월부터 2026년 3월까지, 2,753만 건)를 컴퓨터로 돌려 나온 결과다.

---

## 1. 왜 만들었나

관세청은 우리나라의 수출입 통계를 공개한다. 어느 나라에, 어떤 물건(품목)을, 얼마어치(금액), 얼마나 무겁게(중량) 수출하고 수입했는지를 매달 집계한 자료다. 이 자료는 공공데이터포털(data.go.kr)의 OpenAPI라는 창구로 제공된다. API란 컴퓨터가 자료를 하나씩 요청해서 받아오는 통로를 말한다.

문제는 이 창구가 한 번에 조금씩만 준다는 것이다. "2015년, 미국, 반도체" 하는 식으로 조건을 걸어 하나씩 받아야 한다. 그런데 무역의 흐름을 분석하려면—예를 들어 20년간 대중국 수출이 어떻게 변했는지, 어떤 품목이 새로 등장하고 사라졌는지를 보려면—전 기간·전 국가·전 품목을 다 모아 하나의 큰 표로 통합해야 한다. 그 통합된 표가 바로 데이터베이스다.

이 데이터베이스는 두 가지 목적을 가진다. 하나는 한국 무역의 구조를 분석하는 연구용 자료다. 다른 하나는 학생 교육용이다. 학생들이 실제 대규모 데이터를 다뤄보도록 GitHub(프로그램과 자료를 공개·공유하는 사이트)에 올려, 각자 내려받아 분석하게 한다.

"다시 만들었다"고 하는 이유가 있다. 두 달 전에 초기 버전(v1)을 한 번 만들었는데, 뼈대만 있고 여러 설계 결함을 안고 있었다. 예를 들어 검증 코드가 세 파일로 흩어져 있어 어느 것을 돌려야 할지 불명확했고, 뒤에 설명할 HS 코드 개정 문제를 제대로 해결하지 못해 분석할 때마다 사람이 손으로 연결 작업을 반복해야 했다. KCSDB2는 이런 결함을 없앤 완전한 재구축이다.

## 2. 설계 원칙

가장 중요한 원칙은 하나다. **데이터베이스에는 관세청이 준 원본 자료를 그대로 담고, 분석을 위한 가공은 데이터베이스 바깥에서 한다.**

왜 이렇게 하는지부터 설명한다. 데이터를 저장할 때 "편하라고" 미리 가공해 넣고 싶은 유혹이 있다. 예를 들어 "2015년 3월"이라는 날짜를 저장하면서 "2015"라는 연도 칸을 따로 만들어 두거나, 10자리 HS 품목코드에서 앞 6자리만 잘라 별도 칸에 넣어두는 식이다. 이렇게 하면 나중에 그 칸을 바로 쓸 수 있어 편하다. 그러나 이 편의에는 대가가 있다. 미리 만들어 둔 가공 칸은 "이런 분석을 할 것"이라는 가정을 데이터에 새겨 넣는다. 다른 방식으로 분석하려는 사람에게는 그 칸이 방해가 되고, 무엇보다 원본이 원본 그대로가 아니게 된다. 그래서 이 프로젝트는 가공 칸을 일절 넣지 않았다. 연도가 필요하면 날짜에서 그때그때 계산하고, 6자리 코드가 필요하면 10자리에서 그때 잘라 쓴다.

이 큰 원칙에서 몇 가지 구체적 규칙이 나온다.

**원본 값을 절대 바꾸지 않는다.** 관세청이 준 숫자를 그대로 저장한다. 빈 값을 임의로 채우거나, 음수를 0으로 고치거나, 이상해 보이는 값을 지우지 않는다. 뒤에 나오지만 관세청은 가끔 음수 정정치를 보내는데, 그것도 음수 그대로 보존한다. 데이터를 손대는 순간 그것은 더 이상 관세청의 데이터가 아니라 우리가 해석한 데이터가 되기 때문이다.

**HS 코드 개정 문제는 데이터베이스가 한 번에 해결해 둔다.** 이것이 초기 버전과의 결정적 차이다. HS 코드란 물건을 분류하는 국제 표준 번호다. 반도체, 자동차, 쌀에 각각 고유 번호가 붙는다. 그런데 이 번호 체계는 몇 년마다 개정된다(2007, 2012, 2017, 2022년). 개정 때 어떤 번호는 둘로 쪼개지고, 어떤 번호들은 하나로 합쳐지고, 어떤 번호는 아예 사라진다. 문제는 이것이다. 2010년의 어떤 품목과 2023년의 같은 품목이 개정 때문에 서로 다른 번호를 갖게 되면, 번호만 보고는 "같은 품목의 시간에 따른 변화"를 이을 수 없다. 시계열이 끊긴다. 초기 버전은 이 연결을 분석하는 사람이 매번 손으로 하도록 방치했다. KCSDB2는 개정 간 번호 대응표를 데이터베이스 안에 넣어, 이 연결을 한 번에 해결해 두었다.

**국가 이름은 관세청 코드를 중심에 두고 표준 이름을 곁에 붙인다.** 원본 표에는 관세청이 쓰는 국가 코드를 그대로 두고, 별도의 국가 정보표가 그 코드에 외교부 표준 국가명·국제표준 코드·대륙 정보를 연결한다. 원본은 원본대로 두면서 참조 정보를 따로 붙이는 방식이다.

**층을 나눈다.** 원본 자료 층, 참조·연결 정보 층, 그리고 분석 층. 분석에서 쓰는 개념들—무역이 늘어난 게 새 품목 때문인지 기존 품목의 증가 때문인지 나누는 분석 등—은 어느 것도 데이터베이스에 들어 있지 않다. 이렇게 해야 데이터베이스가 특정 분석을 강요하지 않고, 어떤 분석이든 똑같이 받아들일 수 있다.

## 3. 데이터베이스란 무엇인가

이 절은 데이터베이스·DuckDB·SQL이라는 용어에 익숙하지 않은 독자를 위한 것이다. 이미 아는 독자는 건너뛰어도 된다.

### 스프레드시트와 무엇이 다른가

대부분의 사람은 표라고 하면 엑셀 같은 스프레드시트를 떠올린다. 데이터베이스도 표를 다루지만, 세 가지가 결정적으로 다르다.

첫째, 용량이다. 엑셀 한 장은 약 100만 줄까지만 담는다. 이 프로젝트의 거래 표는 2,753만 줄이다. 엑셀로는 애초에 열 수 없다. 데이터베이스는 수천만, 수억 줄을 다루도록 만들어졌다.

둘째, 여러 표를 연결하는 방식이다. 스프레드시트에서 "국가 코드에 국가 이름을 붙이려면" 보통 VLOOKUP 같은 함수를 칸마다 걸어야 한다. 데이터베이스는 표와 표를 코드로 잇는 "조인(join)"이라는 기능을 기본으로 갖는다. 거래 표의 국가 코드와 국가 정보표를 한 번에 연결해 이름을 붙일 수 있다. 이 프로젝트가 원본 표(거래)와 참조 표(국가·품목·개정 연결)를 나눠 둔 것도, 데이터베이스가 이 연결을 잘하기 때문이다.

셋째, 다루는 방법이다. 스프레드시트는 눈으로 보고 마우스로 클릭해 다룬다. 데이터베이스는 질문을 글로 적어서 다룬다. 그 질문을 적는 언어가 아래의 SQL이다.

### SQL이란

SQL은 Structured Query Language(구조화 질의 언어)의 약자다. 데이터베이스에 "이런 자료를 뽑아 달라"고 요청하는 언어다. 예를 들어 "2020년에 미국으로 수출한 총액을 품목별로, 큰 순서대로 보여줘"를 한 문장으로 적는다. 대략 이렇게 생겼다.

```
SELECT 품목, SUM(수출금액)
FROM 거래표
WHERE 연도 = 2020 AND 국가 = '미국'
GROUP BY 품목
ORDER BY SUM(수출금액) DESC
```

SELECT는 "무엇을 뽑을지", FROM은 "어느 표에서", WHERE는 "어떤 조건으로", GROUP BY는 "무엇 단위로 묶어서", ORDER BY는 "어떤 순서로"를 뜻한다. 엑셀에서 필터·정렬·피벗테이블로 하던 일을 글 한 문장으로 지시하는 것이다. 이 방식의 장점은 같은 질문을 저장해 두고 자료가 바뀔 때마다 다시 돌릴 수 있고, 수천만 줄에도 몇 초 안에 답한다는 것이다.

### DuckDB란

DuckDB는 이 프로젝트가 쓰는 데이터베이스 프로그램의 이름이다. 데이터베이스 프로그램에는 여러 종류가 있다. 은행·쇼핑몰처럼 여러 사람이 동시에 자료를 넣고 빼는 곳은 큰 서버형 데이터베이스(예: PostgreSQL, MySQL)를 쓴다. DuckDB는 그와 달리, 한 사람이 자기 컴퓨터에서 대량의 자료를 빠르게 분석하는 데 특화됐다. 서버를 설치할 필요 없이 파일 하나로 동작하고, 분석에서 흔한 "수백만 줄을 품목별·국가별로 합산" 같은 작업에 최적화돼 있다. 무역통계처럼 한 번 만들어 두고 여러 사람이 각자 내려받아 분석하는 자료에 잘 맞는다.

뒤의 7.3에서 "색인 없이도 충분히 빠르다"고 하는 것이 이 DuckDB의 특성이다. DuckDB는 자료를 세로줄(컬럼) 단위로 저장하고 여러 값을 한꺼번에 계산하는 구조라, 집계 작업이 원래 빠르다.

이 데이터베이스는 kcsdb.duckdb라는 파일 하나로 존재한다. 이 파일 안에 아래 설명할 여러 표가 모두 들어 있다.

### 파이썬(주피터 노트북)과 SQL은 어떻게 연결되나

학생은 주피터 노트북에서 파이썬으로 분석한다. 그런데 방금 SQL을 설명했으니, 파이썬과 SQL이 어떻게 맞물리는지 궁금할 수 있다. 둘은 경쟁 관계가 아니라 분업 관계다.

가장 흔한 방식은 파이썬 코드 안에서 SQL 문장을 실행하는 것이다. 파이썬으로 데이터베이스에 접속한 뒤, SQL 문장을 그대로 넘겨 실행하고, 그 결과를 파이썬 표로 돌려받는다. 코드로 쓰면 대략 이렇다.

```python
import duckdb
con = duckdb.connect("kcsdb.duckdb", read_only=True)
결과 = con.sql("SELECT 국가, SUM(수출금액) FROM 거래표 GROUP BY 국가").df()
```

여기서 큰따옴표 안이 SQL 문장이고, 나머지가 파이썬이다. 데이터베이스에서 수천만 줄을 국가별로 합산하는 무거운 작업은 SQL(데이터베이스)이 빠르게 처리하고, 그 결과로 나온 작은 표를 파이썬이 받아 그래프를 그리거나 추가 계산을 한다. 무거운 일은 데이터베이스에, 시각화·통계는 파이썬에 맡기는 분업이다.

SQL을 거의 안 쓰고 파이썬만으로 다루는 방법도 있다. 데이터를 파이썬 표로 받아온 뒤 파이썬의 표 처리 도구(pandas)로 필터·집계하는 방식이다. 다만 2,753만 줄을 통째로 파이썬으로 끌어와 다루면 느리다(뒤의 7.3에서 다루는 결과 전송 비용). 그래서 큰 집계는 SQL로 미리 줄여서 가져오는 첫 번째 방식이 권장된다. 주피터 노트북은 이 SQL과 파이썬을 한 화면에서 섞어 쓰는 도구다.

## 4. 데이터베이스의 구조

데이터베이스는 여러 개의 표로 이루어진다. 각 표가 무엇을 담는지 설명한다.

**fact_trade(거래 표, 2,753만 3,937줄)** — 이 프로젝트의 핵심 표다. 한 줄이 "특정 월, 특정 국가, 특정 품목"의 수출입 실적 하나다. 담긴 정보는 연월, 국가 코드, 10자리 HS 품목코드, 수출 금액, 수입 금액, 수출 중량, 수입 중량, 무역수지다. 금액 단위는 미국 달러 1,000달러 단위이고, 중량은 킬로그램이다.

**fact_total(총계 표)** — 위 거래 표에서 품목을 빼고 국가별·월별로 합친 표다. "2015년 3월 미국과의 전체 수출입"처럼 품목 구분 없는 총계를 담는다.

**meta_calls(수집 기록 표)** — 데이터를 받아올 때마다 성공했는지, 몇 건을 받았는지, 얼마나 걸렸는지를 기록한 표다. 자료 자체가 아니라 "자료를 어떻게 모았는가"의 이력이다.

**dim_country(국가 정보 표)** — 관세청 국가 코드에 관세청 국가명, 외교부 국가명, 영문명, 국제표준 코드, 대륙을 연결한다.

**dim_hs10(품목 정보 표)** — 10자리 HS 코드에 한글 품목명, 영문 품목명, 수량·중량 단위, 그 코드가 언제부터 유효한지를 연결한다.

**dim_hs6_concordance(HS 개정 연결 표)** — 위에서 설명한 코드 개정 문제를 해결하는 표다. 2022년 기준 6자리 코드가 과거(2007/2012/2017년)의 어느 코드에 대응하는지를 담는다. 관계 종류도 표시한다. 그대로 유지된 코드, 대응되는 코드, 폐지된 코드, 새로 생긴 코드로 나뉜다. 총 1만 8,944줄이다.

표 이름 앞의 fact는 "사실(원본 실적)"을, dim은 "차원(참조 정보)"을 뜻하는 데이터베이스 관례다.

## 5. 데이터를 쌓는 과정

데이터를 받아 데이터베이스로 만드는 과정은 여섯 개의 프로그램(스크립트)으로 나뉜다. 각 프로그램은 따로 실행할 수 있고, 각자 결과를 스스로 점검한다.

**00번 — 어디까지 받았는지 확인** 관세청이 지금 어느 달까지 확정 자료를 냈는지 확인한다. 여기서 중요한 판단 기준이 있다. "총계 금액이 있으면 자료가 있다"가 아니라 "품목별 명세가 있어야 자료가 있다"로 판단한다. 이유는 6.6에서 설명한다.

**02a번 — 원본을 중간 형식으로 변환** 관세청이 주는 원본은 XML이라는 형식이다. 이것을 컴퓨터가 빠르게 읽는 중간 형식으로 바꾼다. 이때 앞서 말한 가공 칸을 넣지 않고 원본 8개 항목만 남긴다.

**02b번 — 데이터베이스에 적재** 중간 형식을 실제 데이터베이스(DuckDB라는 프로그램을 씀)에 넣는다. 넣을 때 가공 칸이 섞여 들어오지 않았는지 검사하고, 아직 확정되지 않은 달(잠정월)을 걸러낸다.

**03번 — 국가·품목 정보표 생성** 국가 정보표와 품목 정보표를 만든다.

**03b번 — HS 개정 연결표 생성** HS 코드 개정 대응표를 만든다. 관세청이 PDF 문서로 공개한 개정 연계표에서 코드 대응 관계를 뽑아낸다.

**04번 — 전체 검증** 완성된 데이터베이스를 다섯 가지 측면에서 점검한다. 표 구조가 맞는지, 값이 이상하지 않은지, 빠뜨린 자료가 없는지, 국가·품목 정보가 제대로 연결됐는지, 개정 연결이 제대로 됐는지를 검사하고, 통과·경고·실패를 보고한다.

이 순서는 반드시 지켜야 한다. 앞 단계가 실패하면 뒤 단계는 의미가 없기 때문이다. 그래서 한 단계씩 실행하고 결과를 확인한 뒤 다음으로 넘어간다.

## 6. 데이터의 함정과 발견

데이터를 다루면서 실제로 부딪힌 함정들이다. 대부분 원본 자료의 특성이거나, 프로그램을 짤 때 놓치기 쉬운 지점이다. 이 함정들이야말로 이 프로젝트에서 가장 배울 것이 많은 부분이다.

### 6.1 나미비아가 사라지는 문제

외교부 국가 코드표에서 나미비아의 국제표준 2자리 코드는 `NA`다. 그런데 데이터를 읽는 프로그램(pandas)은 `NA`라는 글자를 "값이 비어 있음(NULL)"으로 착각한다. 프로그래밍에서 NA나 NULL은 흔히 "빈 값"을 뜻하는 약속이기 때문이다. 아무 조치 없이 국가표를 만들면 나미비아가 "빈 값"으로 처리돼 연결에서 탈락한다. 해결책은 프로그램에 "빈 값 자동 인식을 끄라"고 명시하는 것이다. 글자가 빈 값 기호로 오인되는 이 함정은 데이터에 `NULL`이라는 글자가 실제로 들어 있을 때도 똑같이 생긴다.

### 6.2 관세청은 "없음"과 "0"을 구분하지 않는다

원본을 전부 살펴보니, 숫자 항목은 언제나 값이 채워져 있고, 실적이 없으면 0으로 채워져 온다. "비어 있음"이라는 상태가 아예 없다. 이것은 중요한 뜻을 가진다. 흔히 데이터베이스에서는 "값이 없으면 빈 값으로 두라"고 하는데, 이 데이터에는 그 원칙을 적용할 수 없다. 원본에 빈 값이 없기 때문이다. 실적 0과 자료 없음이 구분되지 않으므로, 분석할 때 이 점을 염두에 둬야 한다.

### 6.3 품목 이름이 반쪽짜리다

관세청 품목 정보 파일의 한글 품목명은 가장 잘게 나눈 최말단 단계의 설명만 담는다. 예를 들어 "농가 사육용", "경주말" 같은 식이다. 그런데 이것이 말(馬)에 관한 것인지, 그 위의 큰 분류가 무엇인지는 그 자체로 알 수 없다. 상위 맥락이 빠져 있다. 이것은 관세청 파일 자체의 한계다. 데이터베이스는 이 반쪽짜리 이름을 그대로 담고, 완전한 설명이 필요하면 상위 코드나 개정 연결표를 통해 분석 단계에서 보충한다. 데이터베이스가 없는 정보를 지어내지 않는다.

### 6.4 "삭제"라고 적힌 폐지 코드

HS 개정 연계표에 `(삭제, 300219)`라고 적힌 줄이 있다. 2017년에 있던 300219라는 코드가 2022년 개정에서 폐지돼 대응하는 새 코드가 없다는 뜻이다. 이 줄을 버리지 않고 "폐지됨"이라고 표시해 보존한다. 어떤 품목이 언제 사라졌는지도 개정 흐름을 분석할 때 필요한 정보이기 때문이다.

### 6.5 음수로 찍힌 중량 19줄

거래 표에 음수가 19줄 있다. 모두 중량이 음수이고 금액은 0 이상이다. 이것은 관세청의 사후 정정이다. 이전에 신고된 중량이 잘못돼 나중에 마이너스로 상계 처리한 것이다. 프로그램 오류가 아니라 원본에 실제로 들어 있는 값이다. 원본 보존 원칙에 따라 그대로 둔다. 이 발견은 검증 방식을 바꾸게 했다. 처음에는 "음수가 있으면 실패"로 검사했는데, 이것이 원본 보존 원칙과 충돌한다는 것을 깨달았다. 그래서 금액 음수는 진짜 오류(실패)로, 중량 음수는 정상적인 정정(정보성 기록)으로 나눠 처리했다. 원칙이 검증보다 우선한다는 판단이다.

### 6.6 관세청은 통계를 두 단계로 낸다 — 잠정월의 함정

관세청은 월별 무역통계를 두 번에 나눠 공개한다. 먼저 국가별 총계(잠정치)를 내고, 나중에 품목별 상세 명세(확정치)를 낸다. 재구축 시점에 2026년 4월·5월은 총계만 나오고 품목 명세가 아직 없는 중간 상태였다. 그런데 처음 만든 확인 프로그램이 "총계 금액이 0보다 크면 자료가 있다"고 판단해서, 이 두 달을 확정된 것으로 잘못 인식했다. 판단 기준을 "품목 명세가 있어야 확정"으로 바꿔서 이 잠정월을 걸러냈고, 확정 범위를 2026년 3월까지로 고정했다. 이것은 확인 프로그램의 판단 기준을 잘못 잡으면 아직 안 끝난 자료를 끝난 것으로 착각한다는 실제 사례다.

### 6.7 수집 기록의 개수가 실제와 어긋난다

수집 기록 표에는 "몇 건을 받았다"는 개수가 적힌다. 그런데 이 개수를 셀 때 총계 줄을 빠뜨린다. 그래서 실적이 0건이지만 관세청이 총계 줄은 보내준 경우, 기록상 개수는 0인데 총계 표에는 1줄이 들어 있는 불일치가 생긴다. 이런 경우가 4,642건이었다. 이 때문에 "받은 개수 = 저장된 줄 수"라는 검증이 어긋났다(4건 차이). 개수가 실제보다 많은 경우와 적은 경우가 뒤섞여 상쇄되면서 작은 잔차만 남은 것이다. 검증 방식을 "관세청이 자료가 있다고 한 경우, 실제로 저장됐는가"로 바꿔서 해결했다. 이것은 검증 지표를 잘못 고르면 데이터가 멀쩡한데도 실패로 보인다는 사례다.

## 7. 완성 후 세 가지 추가 검증

데이터베이스를 완성한 뒤, 세 가지 의문을 추가로 검증했다. 셋 다 "심각해 보였지만 실제로 재보니 문제가 아니거나 조건부"라는 결론이 났다. 이 검증 과정 자체가 배울 점이다. 재보지 않고 "문제일 것"이라고 단정하는 것도, "괜찮을 것"이라고 넘기는 것도 둘 다 근거가 없다.

### 7.1 이름 없는 폐지 코드 문제

10자리 품목코드의 27.2%(4,194종)는 품목 정보표에 이름이 없다. 폐지된 코드들이기 때문이다. 2026년 기준 품목 파일이 과거 폐지 코드를 담지 않는 한계 탓이다. 처음에는 과거 품목 파일을 구해서 이름을 채우려 했으나, 두 가지 이유로 불필요하다고 판단했다.

첫째, 애초에 목표가 어긋났다. 분석을 6자리 수준에서 하면 10자리를 6자리로 자르므로, 잘려 나가는 뒷자리의 세부 이름은 분석에 들어가지 않는다. 필요한 것은 6자리 계열이 무엇인지 식별하는 것뿐이다.

둘째, 그 계열 식별은 이미 해결돼 있다. 폐지 코드 중 거래액 상위 309종(폐지 코드 거래액의 90%)의 6자리 중 308종(99.7%)이 개정 연결표에 들어 있다. 즉 폐지 코드도 6자리로 자르면 어느 계열인지 알 수 있다.

폐지 코드의 거래 비중은 작지 않다(전체의 11.6%, 특히 초기 2007~2011년은 21.4%). 그러나 6자리 분석에서는 세부 이름 자체가 필요 없으므로, 이 비중과 무관하게 문제가 종결된다. 과거 파일을 구할 경로(공공데이터포털의 과거 스냅샷)도 막혀 있음을 확인했다.

### 7.2 개정 연결이 안 되는 사각지대

완성 검증(04번)이 개정 연결 성공률을 66~81%로 보고했다. 이것이 "3분의 1이 연결 안 됨"으로 읽혀 특히 초기 데이터의 신뢰도를 위협하는 것처럼 보였다. 그런데 이 숫자에 두 가지 문제가 있었다.

첫째, 종(種) 수 기준이었다. 연결 안 되는 코드 대부분이 거래액이 극히 작았다. 거래액 기준으로 다시 재니 연결 안 되는 비중이 0.004~0.007%에 불과했다. 종 수로는 3분의 1이 안 이어져도, 그 코드들의 거래액을 합치면 1만분의 1도 안 됐다.

둘째, 시기별로 맞는 개정 버전을 쓰지 않았다. 2009년 자료는 2007년 버전으로, 2015년 자료는 2012년 버전으로 연결해야 맞는데, 처음 검증은 세 버전을 전 기간에 뭉뚱그려 적용한 가정적 숫자였다. 시기에 맞는 버전으로 다시 재니 연결 안 되는 종 수도 124/63/34종으로 훨씬 작았다.

이 두 문제를 걷어내니, 어느 버전으로도 연결 안 되는 진짜 사각지대는 130종, 거래액으로 0.004%였다. 관세청 개정 연계표를 추가로 구할 이유가 사라졌다.

### 7.3 쿼리가 느리지 않은지

분석에서 자주 쓸 무거운 질의(쿼리) 네 가지의 속도를 실제로 쟀다. 그중 가장 무거운 "작년 같은 달과 비교하기"의 순수 계산 시간이 0.9초였다. 네 가지 모두 순수 계산은 1초 안쪽이었다.

일부 질의가 전체 5초로 측정됐는데, 그 시간의 대부분은 계산이 아니라 결과 2천만 줄을 파이썬으로 옮기는 데 든 시간이었다. 데이터베이스 속도를 높이는 색인(인덱스)은 계산을 빠르게 하지 결과를 옮기는 것을 빠르게 하지 않는다. 따라서 색인은 필요 없다고 결론지었다. 이 데이터베이스가 쓰는 DuckDB라는 프로그램은 원래 대량 집계에 최적화돼 있어 색인 없이도 충분히 빠르다. 분석할 때 결과를 통째로 파이썬으로 끌어오지 말고 데이터베이스 안에서 집계를 끝내라는 것이 교훈이다. 이것은 데이터베이스의 결함이 아니라 질의를 짜는 방식의 문제다.

### 7.4 이 판정들은 조건부다

세 판정은 특정 방식의 분석을 전제로 한다. 7.1은 6자리 수준 분석일 때, 7.2는 거래액 크기를 기준으로 볼 때 성립한다. 만약 분석을 10자리 세부 수준으로 내리거나, 거래액 대신 "품목 종류의 개수"를 세는 방식(새 품목이 몇 개 생기고 몇 개 사라졌는지 등)으로 바꾸면 두 판정은 다시 검토해야 한다. 데이터베이스 자체는 특정 분석을 전제하지 않으므로, 이 조건부라는 성격은 데이터베이스가 아니라 판정에만 붙는다. 이 판정들은 별도 기록에 봉인해 두되, 다시 검토해도 되는 조건을 함께 명시했다. 근거 없이 "이거 결함 아니냐"고 다시 파헤치는 것은 막고, 분석 방식이 바뀌어서 정당하게 다시 볼 필요가 있을 때는 허용한다.

## 8. 겪은 실패와 그 수정

이 프로젝트의 가치는 매끄러운 성공담이 아니라 실패와 그 수정에 있다. 실제로 겪은 것들을 기록한다.

**고친 프로그램이 실제로는 안 바뀌어 있었다.** 재구축 도중, 작업 공간에서 고친 프로그램(02b·04번)이 실제 컴퓨터로 옮겨지지 않은 채 옛날 버전이 실행됐다. 결과에 나와야 할 기록이 없어서 이를 알아챘다. AI가 고친 파일과 사용자 컴퓨터의 파일이 저절로 같아지지 않는다는 점을 놓치면 이런 혼선이 생긴다.

**예측이 틀렸다.** 잠정월 486줄을 총계 표에서 빼면 수집 기록과 저장 줄 수의 차이가 490으로 커질 것이라고 예고했는데, 실제로는 차이가 4로 그대로였다. 잠정월의 수집 기록이 애초에 "실패"로 분류돼 개수 합계에 안 들어가 있었기 때문이다. 수집 기록의 분류를 확인하지 않고 추측한 탓이다.

**멀쩡한 것을 결함으로 착각했다.** 7.2에서 다룬 대로, 완성 검증의 연결 성공률 숫자를 처음엔 심각한 결함으로 취급했다. 다시 재보고 나서야 그것이 종 수 기준의 부풀려진 숫자임을 알았다. 검증 지표를 잘못 설계하면 멀쩡한 데이터가 문제로 보인다.

**GitHub 계정이 충돌했다.** 배포 단계에서 컴퓨터에 저장된 로그인 정보가 한 계정으로 돼 있어서, 다른 계정의 저장소에 올리려다 권한 거부를 당했다. 저장된 로그인 정보를 지우고 다시 로그인해 해결했다. 계정을 두 개 쓰는 환경에서 흔한 함정이다.

이 실패들은 "이전 작업 요약을 그대로 믿으면 안 된다"는 교훈으로도 이어진다. 이전 세션의 요약 문서가 사실과 다른 내용(없는 항목, 틀린 통계)을 담은 적이 있었다. AI와 협업할 때 요약 문서를 무비판적으로 믿으면 오류가 그대로 전파된다.

## 9. GitHub 배포

완성된 데이터베이스를 학생 교육용으로 공개했다.

### 9.1 라이선스 확인

공개 배포는 남의 데이터를 다시 배포하는 일이므로, 법적으로 문제없는지 먼저 확인해야 한다. 네 가지 자료의 이용 조건을 확인했다.

- 관세청 수출입실적(핵심 자료): 이용 제한 없음.
- 외교부 국가 코드: 제한 없음.
- 관세청 HS 품목 코드: 공공누리 제1유형. 출처만 밝히면 자유롭게 쓸 수 있다.
- 관세청 HS 개정 연계표: 공공누리 제1유형. 마찬가지로 출처 표시 조건.

네 자료 모두 재배포할 수 있다. 뒤의 둘은 출처를 밝히는 것이 조건이고, 이를 어기면 이용 허락이 자동으로 취소된다. 그래서 저장소 설명과 배포 페이지에 출처를 명시했다. 공공누리 제1유형은 영리 목적도 허용하므로 교육용으로 쓰는 데 제약이 없다. 다만 개정 연계표 PDF에 공공누리 표시가 실제로 붙어 있는지는 확인하지 않았으므로, 엄밀히 하려면 관세청에 문의하는 절차가 남아 있다.

### 9.2 배포 방식

데이터베이스 파일 실물은 681메가바이트다. GitHub 저장소는 파일 하나에 100메가바이트까지만 허용하므로, 이 파일은 저장소에 직접 올릴 수 없다. 그래서 저장소에는 프로그램과 문서만 올리고, 데이터베이스는 GitHub의 "릴리스(Releases)"라는 별도 첨부 기능으로 배포했다. 릴리스는 파일 하나에 2기가바이트까지 허용한다.

올리면 안 되는 것들—데이터베이스 실물, 원본 자료, 그리고 특히 관세청 접속에 쓰는 인증키—이 실수로 올라가지 않도록 제외 목록(.gitignore)을 설정했다. 올리기 전에 실제로 이것들이 빠졌는지 확인했다. 설정 파일과 접속 프로그램에 인증키가 직접 박혀 있지 않은지도 검사했다(인증키는 별도의 제외된 파일에서 읽어오는 구조였다). 실제 올라간 자료 크기가 2.82메가바이트에 그친 것이 데이터베이스가 포함되지 않았음을 확인해 줬다.

데이터베이스는 압축해서 올렸다(681메가바이트에서 326메가바이트로). DuckDB 파일이 이미 내부적으로 압축된 형태라 추가 압축 효과는 절반 정도에 그쳤다. 배포 꼬리표(태그)에는 자료의 기준 시점을 넣어 "v1.0-202603"(2026년 3월 기준)으로 붙였다. 이 꼬리표가 앞으로 만들 분석 챕터나 소개 페이지가 참조할 고정 기준점이다.

배포 후 검증했다. 릴리스에서 파일을 다시 내려받아 압축을 풀고 데이터베이스를 열어, 줄 수(2,753만 3,937)가 원본과 같은지 확인했다. 326메가바이트라는 표시는 파일 손상이 아니라 단위 표기 차이였다.

### 9.3 학생이 쓰는 방법

학생은 자기 컴퓨터에서 주피터 노트북으로 분석한다. 주피터 노트북은 코드와 결과와 설명을 한 화면에서 함께 다루는 분석 도구다. 브라우저에서 바로 쓰는 구글 코랩(Colab)이라는 대안도 있었지만 뺐다. 이유는 교육 목적이다. 이 수업의 목적이 주피터 노트북 사용법을 가르치는 것이므로, 프로그램 설치·파일 배치·주피터 실행을 학생이 직접 해봐야 한다. 코랩은 이 과정을 건너뛰므로 목적에 맞지 않는다.

학생의 작업 순서는 네 단계다. 필요한 프로그램 설치(데이터베이스 도구, 표 처리 도구, 그래프 도구, 주피터), 저장소 내려받기, 릴리스에서 데이터베이스를 받아 정해진 위치에 놓기, 주피터 실행. 저장소에는 시작용 노트북이 들어 있어 접속 방법과 기본 통계 예시를 보여준다. 이 노트북은 특정 분석 방향을 지정하지 않고 방법만 보여준다. 어떤 분석을 할지는 학생이 자유롭게 정한다.
